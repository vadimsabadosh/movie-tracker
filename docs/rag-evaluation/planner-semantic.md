# Plan: FR-8 Viewing Statistics (`GET /stats`)

## Goal
Add a read-only endpoint `GET /stats` that returns summary figures over the whole watch history. It returns the number of watched movies, the average rating, the distribution by genre and the distribution by release year. It follows the layers of ADR-001: a new `StatsRepository` with aggregate SQL, a `StatsService`, a `/stats` route, a Zod schema, and wiring in `container.ts`. It needs no migration and no new dependency. Requirement: FR-8. NFR-1 (aggregation in SQL), NFR-3 (parameters only) and NFR-6 (full OpenAPI) apply.

## Domain facts
| Fact | Source |
|---|---|
| FR-8 figures: number of watched movies, average Rating, distribution by Genre and by years | vault `Viewing Statistics` |
| Implementation: aggregate SQL in the repositories layer, orchestration in the services layer; it is derived from Watch History and not stored | `Viewing Statistics`, `Watch History`, `Services Layer` (planned `StatsService`) |
| The endpoint group is `/stats` | `Routes Layer` |
| One `watches` row per movie, so count rows **without `DISTINCT`**: one rating per movie | ADR-009 (Consequences) |
| Rating is an integer 1–10; the average is overall ("середня загалом") | `Rating` |
| A movie has one or more genres (many-to-many), so a movie counts once in each of its genres | `Genre`, migration 1 |
| Genre keys are compared through `name_key`, and the repository maps snake_case to camelCase | ADR-008, `new-module` skill |
| The catalog holds up to 10 000 movies (NFR-1) | ADR-002, ADR-011 |
| Zod is the single source of truth for response schemas | ADR-004 |
| `watches` has `movie_id` as primary key and `rating` NOT NULL, and `movies.year` is NOT NULL | `src/db/migrations.ts` |

## Decisions
| # | Decision | Why | Rejected alternatives |
|---|---|---|---|
| 1 | `GET /stats` with no query parameters, tag `stats`, response `200 StatsResponse` only | The vault names `/stats`. FR-8 lists four figures over the whole history and does not mention filters. A route with no input has no 400 case | `/watches/stats` mixes it with the history list. `/statistics` contradicts `Routes Layer`. Filters (period, genre) would invent domain rules, see Open question 1 |
| 2 | Response shape: `{ watchedCount: int, averageRating: number \| null, byGenre: [{ genre: string, count: int, averageRating: number }], byYear: [{ year: int, count: int }] }` | The names mirror the vault terms. Arrays of objects keep a stable order. A map keyed by year or genre loses the order and breaks on Cyrillic keys | A bare object map. A nested `distribution: {...}` adds a level with no benefit |
| 3 | `averageRating` is `null` when there are no watches. Round to 2 decimals in SQL with `ROUND(AVG(rating), 2)`. Genre and year arrays are empty `[]` | `AVG` over zero rows already gives `NULL`. Returning `0` would pretend a rating exists. Rounding in SQL keeps the service free of float logic. The 2-decimal precision is my choice, see Open question 2 | `0` for an empty history. Rounding to an integer loses information. Unrounded floats like `7.333333333` are noisy |
| 4 | `byGenre` counts each watch once per genre of its movie, so the sum of counts can exceed `watchedCount`. Sort by `count DESC`, then `name_key ASC`. Show the original `g.name` | Genre is many-to-many, so this is the only way to count per genre without arbitrary choices. `name_key` as a tie-breaker gives a deterministic order (the same approach as ADR-011). The genre name comes from the DB so the casing stays as stored | Counting only the "first" genre invents a rule. Sorting by name only hides the popular ones. Normalising the sum to 100% is not requested |
| 5 | `byGenre[].averageRating` is included (rounded to 2 decimals) | The vault puts "average per genre" in the Preference Profile (FR-6), but it is one extra column in the same `GROUP BY`, and it cannot disagree with the FR-6 data. **Risk:** it overlaps with FR-6, see Open question 3 | Count only: strictly FR-8, but then FR-6 may need the same query again later |
| 6 | `byYear` groups by `movies.year` (release year), not by `watched_at`. Sort by `year ASC`. Only years with at least one watch are returned, with no gap filling | The vault says "розподіл за роками", and the sibling filter `yearFrom/yearTo` in ADR-010 means the release year. Ascending order reads as a timeline. Gap filling over 1888–now would produce thousands of zeros | Grouping by `watched_at` year is another reading, see Open question 4. Decades are not asked for |
| 7 | Four fixed-literal SQL statements, executed in the repository inside `db.transaction(...)` (or one `db.transaction` wrapper that returns all four results) | Statements without input need no parameters (NFR-3). Fixed literals have no string-built SQL. A transaction gives a consistent snapshot, so `watchedCount` equals the sum of `byYear` counts even if a write happens between the queries (better-sqlite3 is synchronous, so this is a cheap guarantee) | One combined query makes the SQL harder to read. Computing the aggregates in JS reads all rows and breaks NFR-1 |
| 8 | `StatsService.get()` is a thin method that returns the repository result | The vault places orchestration in `StatsService`. No business rule exists yet. The service keeps the route from touching a repository (ADR-001) and is the place for future rules | The route calling the repository directly breaks ADR-001. Merging into `WatchService` mixes responsibilities and does not match the vault's planned `StatsService` |
| 9 | No `DISTINCT`, no join to `movies` for `watchedCount` and `averageRating` (use `FROM watches` only) | ADR-009: one row per movie. The join is not needed for these two figures, and `ON DELETE RESTRICT` guarantees that every watch has a movie | `COUNT(DISTINCT movie_id)` contradicts the ADR text. A join adds cost with no benefit |
| 10 | After implementation, run the `record-adr` skill for the response contract (an ADR-012 "Viewing Statistics Contract") and update `Viewing Statistics` plus the MOC | The `new-module` skill (step 6) asks for design choices outside the vault to be recorded, and ADR-010 is the precedent for an endpoint contract. This step needs `ingest_note`, so it is **W6** and is done after the PR, not by the Coder | Burying it in comments, or leaving the contract only in the code |

## Steps
1. **Schema** — create `src/schemas/stats.ts` — done when it exports `GenreStat`, `YearStat`, `StatsResponse` as Zod objects and the types come from `z.infer`. `averageRating` uses `Rating`-compatible bounds: `z.number().min(1).max(10).nullable()` at the top level, and `.min(1).max(10)` per genre. Counts are `z.number().int().min(0)`. Years are `z.number().int()`.
2. **Repository** — create `src/repositories/stats-repository.ts` with class `StatsRepository(db)` and method `summary(): StatsResponse`. It has four constant SQL strings:
   - `SELECT COUNT(*) AS watchedCount, ROUND(AVG(rating), 2) AS averageRating FROM watches`
   - `SELECT g.name AS genre, COUNT(*) AS count, ROUND(AVG(w.rating), 2) AS averageRating FROM watches w JOIN movie_genres mg ON mg.movie_id = w.movie_id JOIN genres g ON g.id = mg.genre_id GROUP BY g.id ORDER BY count DESC, g.name_key ASC`
   - `SELECT m.year AS year, COUNT(*) AS count FROM watches w JOIN movies m ON m.id = w.movie_id GROUP BY m.year ORDER BY m.year ASC`

   Run them in one `db.transaction`. — done when the method returns the four fields typed by the schema, with no string-built SQL and no `${}`.
3. **Service** — create `src/services/stats-service.ts` with class `StatsService(repo)` and `get()` — done when it has no Fastify or SQL imports.
4. **Route** — create `src/routes/stats.ts` with `statsRoutes(app, service)`: `r.get('/stats', { schema: { tags: ['stats'], response: { 200: StatsResponse } } }, () => service.get())` — done when the route is documented in `/openapi.json`.
5. **Wiring** — edit `src/container.ts` (add `stats` to `Services` and `createServices`) and `src/routes/index.ts` (one `await statsRoutes(...)` line) — done when `npm run typecheck` is clean.
6. **Tests** — create `test/stats.test.ts` and extend `test/app.test.ts` (cases below) — done when `npm test` is green.
7. **Verify** — run `npm run typecheck && npm test`, then the three layer-check greps from the `new-module` skill (step 5) — done when the first two greps print nothing and the third has no hit in `stats-repository.ts`.
8. **Report** — return the `new-module` result format, listing the contract decisions as follow-ups for `record-adr`. Do not call `ingest_note`.

## Test plan
| Case | Expected |
|---|---|
| Empty history | `200`, `{ watchedCount: 0, averageRating: null, byGenre: [], byYear: [] }` |
| One movie watched with rating 7 | `watchedCount` 1, `averageRating` 7, one `byGenre` entry per genre, one `byYear` entry with `count` 1 |
| Three watches, ratings 10, 7, 7 | `averageRating` is `8` (24/3 = 8; the Coder picks values that also test rounding: 8, 7, 7 → `7.33`) |
| Movie with 2 genres | The movie counts once in each genre, and `watchedCount` is still 1 (the sum of `byGenre` counts is 2) |
| Movie that is in the catalog but **not** watched | Does not appear in any figure |
| Cancelled watch (`DELETE /movies/:id/watch`) | The figures go back to match the remaining watches |
| `byGenre` order | `count DESC`, ties broken by genre name (Cyrillic genre included) |
| `byYear` order | Ascending by release year; two movies of the same year give `count` 2 |
| Genre average | Equals the mean of the ratings of the watched movies in that genre, rounded to 2 decimals |
| Changing a rating through `PUT` | The averages change on the next call |
| Response validates against `StatsResponse` | No serialization error (Fastify checks the response schema) |
| `app.test.ts`: OpenAPI | `paths['/stats'].get` exists and has no query parameters |
| `POST /stats` | `404` in the common error format |
| Regression | The existing 11 `/watches` parameters and all existing tests stay green |
| Optional: perf | If the Coder adds a test next to `watch-history.perf.test.ts` with 10 000 movies and watches, the `/stats` call stays under the 200 ms budget used in ADR-011 |

## Open questions
| # | Question | Recommended answer | Why it matters |
|---|---|---|---|
| 1 | Should `/stats` accept filters (a period `watchedFrom/watchedTo`, a genre)? | No. FR-8 and the vault list no filters; add optional parameters later, as ADR-010 does for FR-4 | Filters would change the contract and the tests, and they are domain rules the vault does not define |
| 2 | Precision of the average? | 2 decimals (`7.33`) | A client display and the test values depend on it |
| 3 | Should `byGenre` also carry the average rating per genre, given that it overlaps with FR-6 "average rating by genre"? | Yes, include it: it is one extra column and not a separate calculation | If the answer is no, drop `averageRating` from `GenreStat` and from the SQL, which makes the contract smaller |
| 4 | Does "розподіл за роками" mean the release year of the movie or the year of watching? | The release year (`movies.year`), consistent with `yearFrom/yearTo` in ADR-010 | This changes the SQL (`strftime('%Y', w.watched_at)` instead of `m.year`) and the meaning of the result. It is the most important question |
| 5 | A movie with several genres counts in each genre, so the genre counts do not sum to `watchedCount`. Is that acceptable? | Yes, and document it in the schema description | The alternative needs a rule the vault does not have |

## Out of scope
- Filters, pagination, or time windows for the statistics (Open question 1).
- A distribution by director or by rating value, and "top N" limits.
- FR-6 (Preference Profile) and FR-7 (Recommendations), and `src/recommendation/` (W5).
- New migrations or indexes. The aggregates read the whole `watches` table; at 10 000 rows a full scan is acceptable under NFR-1. Revisit only if a measurement shows a problem.
- Multiple views per movie (it would need a new ADR superseding ADR-009).
- Caching of the statistics.
- Writing to the vault (`ingest_note`, ADR-012 and the `Viewing Statistics` update), which happens after review under W6.

# Порівняльне тестування: `search_notes` до і після RAG (ПР № 7)

`search_notes` MCP-сервера `vault` перейшов із пошуку за ключовими словами на семантичний пошук за embeddings ([ADR-012](#рішення)). Сигнатура інструмента не змінилася, конфігурацію агентної IDE (`.mcp.json`, сервер `github`) не чіпали — оновився лише сервер `vault`. Тут — як порівнювали і що вийшло.

## Що змінилося в retrieval

| | До (ПР № 3) | Після (ПР № 7) |
|---|---|---|
| Одиниця пошуку | Нотатка цілком | Розділ `##` нотатки (довгі — частинами до 1200 символів); 38 нотаток → фрагменти з префіксом «назва (aliases) — розділ» |
| Збіг | Підрядок слова (грубий стемінг) у назві, aliases, тегах, тілі | Косинусна близькість embeddings `multilingual-e5-small` (384 виміри), українська й англійська в одному просторі |
| Що бачить агент | Назва + один рядок до 200 символів | Назва, розділ, текст розділу до 700 символів |
| Сховище | — (перебір файлів) | LanceDB у `harness/vault-mcp/.index/` (embedded, без сервера; у `.gitignore`) |
| Резерв | — | Пошук за ключовими словами: `VAULT_SEARCH=keyword` або при збої моделі/індексу |

Повний цикл: запит агента → `search_notes` → embedding запиту (`query: …`) → векторний пошук у LanceDB з фільтрами `type`/`tag` → N найближчих фрагментів → JSON у контекст агента. Перед пошуком сервер звіряє хеші нотаток і повторно вбудовує лише змінені; vault лишається джерелом істини, індекс можна видалити й перебудувати (`npm run reindex`).

## Методика

Ті самі 10 питань ([`questions.json`](questions.json)) у двох режимах одного сервера — відрізняється лише `VAULT_SEARCH`. Питання різної складності: факти, обґрунтування рішень, перефразування (слова питання не збігаються зі словами нотатки), питання англійською до українських нотаток, питання на кілька нотаток, планування.

1. **Retrieval** (`npm run eval`, детерміновано): чи потрапляє нотатка з відповіддю в топ-5 різних нотаток. → [`retrieval-results.md`](retrieval-results.md)
2. **Відповіді агента** (`npm run eval:agent`): кожне питання — свіжому headless-агенту Claude Code (`claude-sonnet-5-5`) у порожній тимчасовій директорії, без CLAUDE.md, пам'яті й плагінів користувача; єдиний інструмент — `search_notes` (`get_note` вимкнено, щоб відповідь залежала саме від пошуку, а не від навігації по MOC). → [`agent-runs.json`](agent-runs.json)
3. **Skills і оркестрація** (`npm run eval:planner`): роль Planner (`.claude/agents/planner.md`, ПР № 6) планує FR-8 у репозиторії застосунку зі звичайними інструментами й guardrails. → [`planner-keyword.md`](planner-keyword.md), [`planner-semantic.md`](planner-semantic.md)

Оцінку відповідей виставлено вручну за текстом нотаток vault: **повна** — усі суттєві факти з нотатки; **часткова** — правильна, але без ключового факту, або з позначеною здогадкою; **немає** — агент не зміг відповісти.

## Результати

### 1. Retrieval

| Метрика | keyword (до) | semantic (після) |
|---|---|---|
| Очікувана нотатка першою | 6 / 10 | **10 / 10** |
| Очікувана нотатка в топ-5 | 8 / 10 | **10 / 10** |
| Середній recall@5 | 0.77 | **0.92** |
| MRR | 0.67 | **1.0** |

Найбільший виграш — на перефразуваннях: Q7 «taste profile» (нотатка називається Preference Profile, тіло українською) і Q9 «edit the knowledge base files» (ADR-005 говорить про «vault» і «прямий доступ») — keyword не знайшов нічого релевантного в топ-5. Q1 і Q4 keyword знайшов лише третіми. Де питання містить точні терміни нотатки (Q2, Q3, Q5, Q8), обидва режими рівні.

Галюцинацій не було в жодному режимі: системна інструкція «якщо в базі немає — скажи» спрацювала, і keyword-агент чесно писав «у фрагментах цього немає» або позначав здогадку. Тобто з keyword-пошуком збій проявляється як **неповнота**, а не вигадка. Semantic-агенту вистачало двох пошуків (запит англійською й українською), keyword-агент робив третій, звужений запит — і все одно не бачив тексту. Semantic дорожчий на ~$0.01 за відповідь, бо в контекст потрапляють довші фрагменти — це і є ціна RAG.

### 3. Skills і оркестрація: Planner на FR-8

| | keyword | semantic |
|---|---|---|
| Виклики vault | 12 (2 × `search_notes`, 10 × `get_note`) | 12 (2 × `search_notes`, 10 × `get_note`) |
| Ключові нотатки | MOC, Viewing Statistics, ADR-009, ADR-010, шари | MOC, Viewing Statistics, Watch History, ADR-009, шари, Database |
| Ключовий наслідок ADR-009 (рахувати без `DISTINCT`) у плані | так | так |
| Ходів / час / вартість | 26 / 53 с / $0.25 | 31 / 63 с / $0.28 |

Плани рівноцінні. Planner за інструкцією починає з MOC і йде типізованими зв'язками через `get_note`, а `search_notes` використовує лише двічі; MOC (ПР № 2) і онтологія (ПР № 4) вже ведуть його до потрібних нотаток. Тому для навігованих задач на кшталт T1–T5 поліпшений пошук майже не змінює результат — він важливий там, де агент не знає назви нотатки: питання своїми словами, іншою мовою, пошук «чи є рішення про X». Skills і ролі отримали це без змін у своїх файлах — вони викликають той самий `search_notes`.

## Висновки

1. Семантичний `search_notes` усуває головну слабкість keyword-пошуку — розрив між словами питання і словами нотатки (перефразування, англійська проти української): нотатка з відповіддю першою в 10/10 замість 6/10.
2. Для агента більше важить **що** повертається, ніж **як** знайдено: фрагмент-розділ замість рядка-сніпета дав 10/10 повних відповідей замість 4/10 без `get_note`. З `get_note` keyword-агент зміг би дочитати нотатку — ціною зайвих викликів.
3. Галюцинацій 0/20 в обох режимах; поліпшення — у повноті й точності, а не в «чесності».
4. Для оркестрації ефект малий: Planner навігує по MOC і зв'язках. Це аргумент за поєднання — структура vault для відомого, семантичний пошук для невідомого.
5. Обмеження: 10 питань і один прогін на режим — відповіді LLM недетерміновані, тож оцінки показові, а не статистичні; оцінювання ручне. Retrieval-метрики (`npm run eval`) детерміновані й відтворювані.

## Відтворення

```bash
cd harness/vault-mcp
npm run eval           # retrieval, ~15 с, без витрат на API
npm run eval:agent     # 20 headless-прогонів, ~1 хв, ≈$0.7
npm run eval:planner   # 2 прогони Planner, ~1 хв, ≈$0.5
```

## Рішення

Вибір LanceDB + `multilingual-e5-small`, chunking за розділами й резервний keyword-режим зафіксовано у vault: **ADR-012 Semantic Search with Embedded LanceDB Index**.

# Skills harness (ПР № 5)

Два skills Claude Code у `.claude/skills/`. Агент викликає їх за назвою (`/new-module`, `/record-adr`) або сам, коли запит відповідає опису (`description` у frontmatter).

| Skill | Задача з ПР № 1 | Що робить | Шари harness |
|-------|-----------------|-----------|--------------|
| `new-module` | **T1** — каркас нового модуля | Схема Zod, репозиторій, сервіс, маршрути, міграція й тести за ADR-001; шаблони в `templates/` | vault (домен), guardrails (A2/W3/W4/W5/B6), перевірки (A3) |
| `record-adr` | Фіксація рішень (ПР № 1, розділ 2, джерело 2) | ADR у `Decisions/` через MCP-конектор, номер, перевірка дублікатів, зв'язки `governed_by` / `supersedes` | vault (retrieval + ingestion), онтологія (ПР № 4), guardrails (W6, B4) |

## 1. Структура skill

Обидва мають однакову будову (`SKILL.md`):

1. **Коли застосовувати.** `description` у frontmatter, за яким агент розпізнає контекст, і розділ «Не для».
2. **Звернення до бази знань.** Обов'язковий перший крок: `get_note` / `search_notes`. Правило «якщо нотатки немає — зупинись і запитай, не вигадуй».
3. **Перевірка guardrails до дії.** Таблиця файлів чи дій із ID правил із `docs/guardrails.md` і очікуваною реакцією hook. Відмова hook — це знахідка для звіту, а не перешкода, яку слід обходити.
4. **Процедура.** Кроки з конвенціями (`new-module`) або формат ADR за Nygard (`record-adr`).
5. **Перевірка результату.** `npm run typecheck && npm test` і grep-перевірка шарів для `new-module`; `get_note` зі зворотними зв'язками для `record-adr`.
6. **Фіксований формат результату.** Однакові таблиці з розділами, щоб результат могла прочитати людина й інший агент у ПР № 6.

## 2. Застосування до реальних задач

Чотири задачі розробки застосунку, послідовно, в одній сесії Claude Code, гілка `pr5`.

| # | Skill | Задача | Результат | Коміт |
|---|-------|--------|-----------|-------|
| 1 | `new-module` | Movie: CRUD каталогу + пошук (FR-1, FR-5) | 5 ендпоінтів, міграція 1, 20 тестів | app `c239213` |
| 2 | `record-adr` | Порівняння тексту без регістру для кирилиці | ADR-008 + `governed_by` для 2 компонентів | vault `21cd8a4`, `40d3b44`, `d263c3b` |
| 3 | `new-module` | Watch Entry: позначка, оцінка, скасування (FR-2, FR-3) | 5 ендпоінтів + 409 на видалення фільму, міграція 2, 21 тест | app `6344406` |
| 4 | `record-adr` | Один перегляд на фільм, історія зберігається при видаленні | ADR-009 + `governed_by` для 2 компонентів і концепту | vault `e294dff`, `24eb1d3`, `e154217`, `fab5071` |

Підсумок: застосунок має 45 тестів, typecheck і перевірка шарів чисті, OpenAPI генерується з тих самих схем (`/openapi.json`).

### Задача 1 — `new-module` → Movie

- **Спрацювало.** Атрибути та правила з нотаток Movie, Genre, Director, ADR-001, ADR-004; файли за шаблонами; перевірки й grep шарів.
- **Зупинка за правилом skill.** Vault не задавав діапазону `year`, способу створення жанрів і правила дублікатів. Skill зупинився й запитав людину, а не вигадав. Відповіді записано в результат як «не з vault — від людини».
- **Ручне втручання (3), виправлено в skill і шаблонах.**
  1. Крок «зареєструй у `routes/index.ts`» призвів до створення репозиторію в шарі маршрутів, що порушує власну grep-перевірку skill. Додано корінь композиції `src/container.ts`, крок skill переписано.
  2. `create(body: unknown)` у шаблоні тестів не проходив typecheck. Замінено на `object`.
  3. better-sqlite3 не приймає нумеровані `?1`, а `${where}` у SQL ловить grep NFR-3. Skill тепер вимагає іменованих параметрів `@q` і забороняє SQL із шаблонних рядків.
- **Знахідка skill.** SQLite `NOCASE`/`LIKE` не згортає кирилицю. Крок 6 skill передав рішення в `record-adr` (задача 2).
- **Guardrails.** Усі файли — A2. Міграція — W3: hook запитав підтвердження.

### Задача 2 — `record-adr` → ADR-008

- **Спрацювало повністю.** Перевірка дублікатів (знайдено пов'язаний ADR-002, без суперечностей), номер 008 за найбільшим наявним, формат Nygard, `governed_by` для Repositories Layer і Database. `get_note` підтвердив зворотні зв'язки, попереджень 0.
- **Уточнення процесу.** Щоб `source` був справжнім SHA, код закомічено до ADR. У результаті skill записано як рекомендацію: спершу коміт, потім ADR.
- **Guardrails.** 3 записи — W6: кожен підтверджено людиною. Прямого доступу до vault не було (B4).

### Задача 3 — `new-module` → Watch Entry

- **Спрацювало.** Правило «повторна позначка → 409» skill знайшов у нотатці Error Handling, тож воно не стало питанням до людини. Тести пройшли з першого запуску.
- **Зупинка за правилом skill.** Правила дати перегляду, поведінка видалення фільму з історією та обов'язковість оцінки не були у vault. Їх запитано в людини.
- **Ручне втручання (2), поза моделлю skill.**
  1. Skill передбачає «одна сутність = `/<entities>`». Watch Entry вкладено в Movie (`/movies/:id/watch`), і він змінює наявний `MovieService.delete`. Шаблони адаптовано вручну. Skill не покриває вкладені ресурси та зміни наявних модулів (розділ 3).
  2. Правило «не в майбутньому» залежить від годинника, тож Zod його не перевірить. Додано `DomainValidationError` (той самий формат 400) та ін'єкцію `today` для детермінованих тестів.
- **Guardrails.** A2 для всіх файлів, W3 для міграції 2.

### Задача 4 — `record-adr` → ADR-009

- **Спрацювало.** Дублікатів немає; ADR формалізував неявне правило з Error Handling і його наслідки (повторні перегляди не зберігаються) з трьома альтернативами.
- **Розширення skill.** Рішення змінює доменне правило, тож `governed_by` отримав і концепт Watch Entry, а не лише компоненти. Онтологія це дозволяє (домен `governed_by`: component, concept). Крок 3 skill оновлено, щоб це було явно.
- **Guardrails.** 4 записи — W6.

## 3. Висновки

**Де skills спрацювали коректно:**

- Звернення до vault на першому кроці дало правила, які інакше довелося б вигадувати: 1–10, 409 на повторну позначку, багато-до-багатьох для жанрів.
- Правило «немає у vault — запитай» спрацювало 6 разів (3 + 3 питання). Жодне доменне правило не вигадано.
- Перевірка guardrails до дії збіглася з фактичною реакцією hook (A2 без діалогу, W3 і W6 з діалогом). Відмов (B) не було: skill не пропонує заборонених дій.
- Фіксований формат результату дав однакові звіти для всіх чотирьох задач.
- `record-adr` не потребував ручних виправлень.

**Де знадобилось ручне втручання:**

| Випадок | Причина | Виправлення |
|---------|---------|-------------|
| Репозиторій у шарі маршрутів | Суперечність між кроками skill | Додано `container.ts`, крок переписано |
| Тип payload у шаблоні тестів | Помилка шаблону | Шаблон виправлено |
| Нумеровані параметри SQL, SQL із шаблонних рядків | Невідома особливість драйвера | Правило в skill |
| Вкладений ресурс і зміна наявного модуля | Поза моделлю skill | Вручну; кандидат на розширення |
| Правило, що залежить від годинника | Zod не бачить «сьогодні» | `DomainValidationError` + ін'єкція `today` |

**Чого навчило тестування:** перший запуск skill на реальній задачі — це його тест. Три з п'яти втручань були дефектами самого skill, і їх виправлено одразу, тому друга задача `new-module` пройшла без них. Решта два — межі моделі skill, задокументовані тут, а не приховані.

**Далі (ПР № 6):** результат `new-module` має фіксований розділ «Follow-ups», з якого оркестратор може автоматично викликати `record-adr`. Рев'ювер (T3) може використати grep-перевірку шарів із кроку 5 як готовий чекліст.
